# Findings in the existing SLAMurai setup (each checked against the Dashing sources or the files; none changed in `SLAMurai/`)

Ordered by how likely they are to be behind "Nav2 is a headache to tune".  "Confirm" = needs one command on the robot.

| # | Finding | Evidence | Effect | Action (applied in `config/nav2_params.derived.yaml` unless noted) |
|---|---|---|---|---|
| 1 | DWB subscribes to the topic `odom` by default (`OdomSubscriber("odom")`, override with `odom_topic`). This stack publishes `/odometry/raw` and the EKF's `/odometry/filtered`, not `/odom`. | `nav_2d_utils/odom_subscriber.hpp` (dashing-devel); `slamurai_launch.py`, `ekf.yaml` | If nothing publishes `/odom`, DWB believes the robot is always standing still: velocity window is centred on 0 every cycle, which looks like sluggishness and jerk and makes accel limits meaningless | `odom_topic: /odometry/filtered`. **Confirm**: `ros2 topic info /odom` |
| 2 | `BaseObstacle.scale: 20`. DWB sums `scale x raw score`; BaseObstacle's raw score is a costmap cost (0-253), the path/goal scores are distances in cells. Dashing's reference config uses 0.02. | `nav2_bringup/launch/nav2_params.yaml` (dashing-devel): BaseObstacle 0.02, PathDist 32, GoalDist 24 | Obstacle term ~1000x the intended weight: any inflation cost dominates, robot dithers or freezes in doorways. In the offline surrogate the user's value stalled most scenarios; 0.02 did not | kept as the start value so you can compare; the tuner's range is 0.005-100 (log) and the first stage tunes it |
| 3 | `controller_server:` and `recoveries_server:` blocks (and `progress_checker:` inside them) are not read by any Dashing node | `nav2_bringup_launch.py` starts `dwb_controller`, `navfn_planner`, `recoveries_node`, `bt_navigator`, `lifecycle_manager`, `world_model` with the shared file but `recoveries_node` gets only `use_sim_time`; no node declares those names | Edits there do nothing. Progress checker runs on its defaults (0.5 m in 10 s) | none needed; `dashing_keys.py` reports them |
| 4 | Global costmap `scan.obstacle_max_range: 11.5` / `raytrace_max_range: 11.5` are not Dashing parameter names (`obstacle_range`, `raytrace_range`) | `obstacle_layer.cpp` (dashing-devel) | Global costmap marks/clears only within the defaults 2.5 m / 3.0 m | renamed, 5.0 / 5.5 |
| 5 | `Oscillation.oscillation_reset_dist/angle` (dotted) are read as plain `oscillation_reset_dist/angle` | `oscillation.cpp`: `searchAndGetParam(nh_, "oscillation_reset_dist", ...)` | Your values equal the defaults, so no effect today; tuning them would silently do nothing | plain names |
| 6 | Map yamls use `free_thresh: 0.25` with slam_toolbox's unknown = 205: occ = 1 - 205/255 = 0.196 < 0.25, so map_server publishes unknown as FREE | `occ_grid_loader.cpp` (trinary branch); histogram of `firstfloor_360.pgm`: 23 014 px at 205 vs 31 273 at 254 | About 40 % of the first-floor map's "free" space is unobserved; the planner may route through it and AMCL/costmaps treat it as free | **not changed**: set `free_thresh: 0.196` in the map yaml (and re-check goals) |
| 7 | `robot_radius: 0.15`; CAD v17 circumradius is 0.175 (dome wall R175, camera pod corner 0.172) | `robot_cad/v17/gen/design10.py` `WALL_RO`, `boxes.json` | Planner can put the dome 2.5 cm into obstacles | 0.185 (CAD + 1 cm pad) |
| 8 | Firmware `motor_controller_xdrive.ino`: wheel-centre radius 0.151 (CAD: 0.133), per-wheel clamp (distorts direction at the cap), no input validation, timeout 0.5 s, `max_vel` 0.25-0.35 asks for more wheel speed than the 5000 steps/s cap gives (0.2916 m/s) | `.ino`, `CONTROL_NAV_PROPOSALS.md` F1/F2 | yaw odometry 14 % off, path drift, planner's kinematics wrong | new `motor_controller_xdrive_safe` (0.133, common wheel scale, 0.21 m/s, 0.5 rad/s). **Spin-test and trim R** (comment in file) |
| 9 | `CONTROL_NAV_PROPOSALS.md` N8 proposes `obstacle_min_range`; Dashing's obstacle layer has no such parameter | `obstacle_layer.cpp` | would be ignored | not used; blade/self returns are handled in the gate and by `laser_min_range` |
| 10 | Dashing reads parameters once at node start-up (no parameter-event callbacks, `nav2_dynamic_params` is not wired into DWB, costmaps, AMCL) | `dwb_local_planner.cpp`, `inflation_layer.cpp`, `amcl_node.cpp`: only `declare_parameter`/`get_parameter` in `on_configure` | `ros2 param set` on a running stack changes nothing | autotune restarts Nav2 per candidate (`nav2_only_launch.py`) |
| 11 | rclpy in Dashing has no action client; `ros2 action send_goal` is not available | Dashing release | goals go through `/move_base_simple/goal` (what `cortex/slamurai_interface.py` already does); completion is judged from pose + velocity | built in |
| 12 | README says Jetson Xavier NX; you say TX2; CAD has a TX2 devkit | README, `robot_cad` | compute budget in `robot_profile.yaml` assumes TX2 numbers | adjust `compute:` |
